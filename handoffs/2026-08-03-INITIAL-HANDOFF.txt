6) Database Contract — ใช้คุมฐานข้อมูล
==================================================

ตารางหลัก:
1. users
2. student_profiles
3. skills
4. user_skills
5. exchange_requests
6. notifications
7. jobs
8. failed_jobs

users:
- id, name, student_code, email, password
- role: student/admin
- status: active/suspended
- email_verified_at, remember_token, timestamps

student_profiles:
- id, user_id, faculty, major, year_level
- bio, phone, contact_channel, profile_image, timestamps
- user_id เป็น Unique
- One-to-One กับ users
- year_level 1–8

skills:
- id, name, category, is_active, timestamps, deleted_at
- หมวดหมู่ตัวอย่าง: เทคโนโลยี ภาษา การออกแบบ ธุรกิจ วิชาการ งานอดิเรก

user_skills:
- id, user_id, skill_id, skill_type, description, timestamps
- skill_type: offered/wanted
- UNIQUE(user_id, skill_id, skill_type)

exchange_requests:
- id, sender_id, receiver_id
- sender_user_skill_id, receiver_user_skill_id
- learning_format: online/onsite/either
- preferred_schedule, message
- status, responded_at, completed_at, timestamps

สถานะ:
- pending
- accepted
- rejected
- cancelled
- completed

Transition ที่อนุญาต:
- pending -> accepted
- pending -> rejected
- pending -> cancelled
- accepted -> completed

กฎ:
- sender ห้ามเท่ากับ receiver
- sender skill ต้องเป็นของ sender และเป็น offered
- receiver skill ต้องเป็นของ receiver และเป็น offered
- receiver ต้อง active
- ป้องกัน pending request ซ้ำ
- ห้าม Hard Delete คำขอ
- ต้องรักษาประวัติ

กฎสำคัญ:
Database Contract ใช้คุม Schema, Field, Relationship, Foreign Key, Index, Unique Constraint และ Delete Behavior ห้าม Codex เปลี่ยนฐานข้อมูลเอง

7) User Flow
==================================================

Student Entry:
เปิดเว็บไซต์ -> สมัครหรือ Login -> ตรวจ role/status -> active ไป Dashboard -> suspended ถูกบล็อก

First-Time Setup:
กรอกคณะ สาขา ชั้นปี แนะนำตัว ช่องทางติดต่อ -> อัปโหลดรูป -> เพิ่ม offered skill -> เพิ่ม wanted skill -> พร้อมค้นหา

Search:
ค้นหาด้วยชื่อ ทักษะ คณะ ชั้นปี
- ไม่แสดงตนเอง
- แสดงเฉพาะ active user
- มี Empty State และปุ่มล้างตัวกรอง

Send Request:
ดูโปรไฟล์ผู้อื่น -> เลือก skill ของตน -> เลือก skill ของผู้รับ -> เลือกรูปแบบ -> ระบุเวลาสะดวก -> ข้อความ -> Validate -> สร้าง pending -> Observer -> Queue -> Email ผู้รับ

Incoming:
- ผู้รับ Accept: pending -> accepted
- ผู้รับ Reject: pending -> rejected

Outgoing:
- ผู้ส่ง Cancel: pending -> cancelled

Complete:
- ผู้ส่งหรือผู้รับ: accepted -> completed
- แจ้งทั้งสองฝ่าย
- เวอร์ชันนี้ไม่ใช้ระบบยืนยันสองฝ่ายเพื่อคง Scope ให้เล็ก

8) Queue, Notification และ Observer
==================================================

ใช้ ExchangeRequestObserver กับ created และ updated
Observer มีหน้าที่ตรวจเหตุการณ์และ Dispatch Notification/Job เท่านั้น
ห้ามใส่ Business Logic ขนาดใหญ่ใน Observer
ห้ามส่งอีเมลแบบ Blocking ใน Controller

เหตุการณ์แจ้งเตือน:
- คำขอใหม่ -> ผู้รับ
- Accepted -> ผู้ส่ง
- Rejected -> ผู้ส่ง
- Cancelled -> ผู้รับ
- Completed -> ทั้งสองฝ่าย

Local Development:
- QUEUE_CONNECTION=database
- MAIL_MAILER=log หรือ Mail Sandbox

Test:
- Notification::fake()
- Mail::fake()
- Queue::fake()
